BUG 1 — [HIGH] Race on the module-global `_prev_net` network state
FILE: scanner/hardware.py  (declare near line 99; use in collect_network, lines 213-243)

CURRENT:
    _prev_net: dict[str, float] = {"sent": 0, "recv": 0, "t": 0.0}
    ...
    prev_sent = _prev_net.get("sent", 0)
    prev_recv = _prev_net.get("recv", 0)
    prev_t = _prev_net.get("t", 0.0)
    if prev_t and now > prev_t:
        dt = now - prev_t
        snap.up_bps = _rate_bps(snap.bytes_sent, prev_sent, dt)
        snap.down_bps = _rate_bps(snap.bytes_recv, prev_recv, dt)
    ...
    _prev_net.update({"sent": snap.bytes_sent, "recv": snap.bytes_recv, "t": now})

WHY IT IS A BUG:
`collect_network()` is called concurrently from three places: the monitor thread
(monitoring.MonitorWorker._loop), the manual-refresh thread (ScannerApp._collect_job)
and the scan thread (ScannerApp._scan_job). `_prev_net` is read/compute/written with no
lock, so threads interleave: `dt` can collapse to a few milliseconds (absurdly inflated
Mbps) and a newer timestamp can be overwritten by an older one (false "counter reset",
rate reported unavailable). Only reproducible when a manual refresh or scan overlaps
live monitoring.

FIX:
- Add `import threading` and a module-level `_net_lock = threading.Lock()`.
- Perform the read of prev values, the `_rate_bps` calls, and the `_prev_net.update(...)`
  inside a single `with _net_lock:` block. Do not hold the lock while calling psutil.
- Keep `_rate_bps` unchanged.
- Add a test: two threads collecting in a loop must never produce a negative rate and
  must never raise; or assert the update block is lock-guarded by patching the lock.

FILE: scanner/app.py  lines 467-498 (_poll_bg_queue) and 626-645 (_poll_monitor)

              pass
- Use it at the end of `_poll_bg_queue` and `_poll_monitor`.
- Remove the duplicate `after()` scheduling inside `toggle_monitoring` if the helper
